# iPhone 捷徑通知記帳

這個功能接收你私人捷徑送來的街口通知，先放入待確認收件匣。它不是街口官方消費者帳戶串接，不讀取街口帳密，也沒有街口或 Apple 的交易簽章。持有連線金鑰的人可以提交通知；請只放在自己的私人捷徑中。

## 可以做到什麼

- 登入柴柴記帳後，從「帳戶與同步 → iPhone 捷徑記帳」建立連線，複製接收網址及只顯示一次的專用金鑰。
- 通知在雲端收件匣保留原文、建議金額、商家及時間，確認帳戶、支出分類、實付金額後入帳。
- 測試通知只測接收，不改餘額；訪客可使用完全在本機執行的文字解析測試。
- 只有人工確認過且帶有來源識別碼的支援格式，才可設定自動入帳；開啟前還須由你確認已在 iPhone 重送測試，同一通知的來源 ID 不變。系統無法替支付平台證明 ID 的真實性或穩定性。缺少識別碼、格式改變、儲值、折抵、多金額或疑似重複都保留待確認。
- 每個帳號同時只能有一個未停用的自動入帳連線，其他連線使用待確認模式。切換前先把舊連線改回待確認或停用；不會為了開啟新連線而悄悄改掉舊設定。

目前沒有 iPhone 真機端到端驗收證據。App 內的通知截圖不等於捷徑拿得到完整推播；能否在鎖定畫面、背景、網路恢復後取得需要的欄位，要由實際手機確認。不能承諾每次消費全自動，也不能從一張 Apple Services 通知辨識每筆實際購買的 App；用途可在確認時自行修改。

以下是 iOS 27.1 的設定指引，通知欄位選取方式參考 [Spenvo 設定說明](https://spenvo.app/setup/)（2026-10-11 核對）。該來源將 Title、Subtitle、Body 合在一份文字；本 App 將 Title 獨立傳入 `title`，只有非空 Subtitle 和 Body 合成 `text`。這不代表本 App 已完成真機驗收。手機沒有該選項、無法取得內文或沒有可靠事件 ID 時，以手機實際能力為準，保持待確認流程。

## 第一次設定

1. 先登入並完成帳本同步。若有衝突、未同步資料或本機復原提示，先處理，再選擇扣款帳戶及分類。
2. 在「連接 iPhone」建立金鑰。離開此頁後無法再查看；遺失時停用舊連線，建立新的。
3. 在 iPhone「捷徑」新增一個捷徑，在**同一捷徑**內加入 Automation → Apps → Notification 觸發器，選擇街口支付，先不啟用自動執行。下列欄位整理與 HTTP 傳送動作也放在這個捷徑中。手機顯示名稱或選項可能不同，須由實際 iOS 27.1 確認。
4. 加入「取得 URL 的內容」，URL 使用 App 顯示的接收網址，方法為 `POST`。
5. 加入 `Content-Type: application/json` 及 `Authorization: Bearer <你的專用金鑰>` 標頭。金鑰不要放 URL、JSON、公開捷徑、截圖或聊天。
6. 要求本文選 JSON，先手動執行以下合成範本。`version` 是數字 `1`，`source` 是文字 `jkopay`，`test` 是布林值「真」。`test` 是必要欄位，漏填或填成文字會被拒絕，不會默認為正式通知。這份資料不能視為真實消費，不含來源 ID 或交易日期：

```json
{
  "version": 1,
  "source": "jkopay",
  "title": "合成測試通知",
  "text": "Example Services\n合成測試：成功扣款 TWD 125.50",
  "test": true
}
```

7. 回到「通知收件匣」重新整理，核對合成測試列未入帳。接收不到時，不要改成正式模式；這次成功只證明 HTTP 接收合成範本，不能證明通知觸發、背景或鎖定畫面執行成功。
8. 再接上 Notification 觸發器實際提供的欄位。點通知變數 token 選屬性：`Notification.Title` 獨立接到 JSON 的 `title`。不要假設 **Shortcut Input／捷徑輸入** 有通知內容，不要傳整個 Notification 物件的描述。
9. JSON 的 `text` 只取 `Notification.Subtitle` 與 `Notification.Body`。用「如果」判斷各欄是否有值；兩者都有值時，建立「文字」動作，第一行放 Subtitle、按一次換行、第二行放 Body；只有一欄非空就使用該欄。把這份文字的輸出接到 `text`，**不要再加 Title**。兩欄皆空時先停止傳送並查欄位／通知權限，不能用目前時間或自造內容補成交易。
10. 保持 `test: true`，在手機實際通知觸發後核對收件匣 `title` 和 `text` 的原文。未驗證欄位與執行方式前，保持測試模式。鎖定畫面、背景、離線後恢復的行為仍需另做真機驗證。
11. 確定傳輸正確後才將 `test` 改為布林值「假」。沒有可靠來源 ID 就省略 `eventId`，新通知保持待確認。核對交易日期、帳戶與金額後才能人工確認入帳，不需另建立同一筆支出。每次隨機 UUID、通知日期、目前日期或金額拼接都不能當作穩定來源 ID。
12. 只有來源提供**同一通知重送也不變**的可靠 ID 才可填 `eventId`。要考慮自動模式，仍須先核准一筆帶來源 ID、且原文與解析結果一致的正式通知，再以相同通知重送確認 ID 不變；完成真機驗證後才可勾選相關確認。不能因合成測試成功就開啟自動入帳。

選擇的帳戶要符合你的帳本：通知不一定提供真正的扣款銀行或卡片。對於自動儲值加消費的組合，這個功能只讓你確認一筆支出，不會額外造一筆儲值、收入或轉帳；若你同時追蹤錢包與來源帳戶，儲值仍須依既有轉帳流程記錄。

## 金額、時間及重送

接收內容有 8 KiB 上限。明確支援 TWD 正數、最多兩位小數；不是金額的點數和優惠不能當作扣款。不會對通知中的最終扣款再次扣除折抵，任何混合金額都需要你確認。

有日期的通知以內文消費時間解析；街口本文日期依台北時區 `+08:00`。選填 `occurredAt` 必須是實際交易日期且包含時區，不能用通知發送／收到時間、Notification 的日期或目前時間代替。缺少或不能辨識的日期由你確認，不用「目前日期」動作補值。

同一連線中，穩定 `eventId` 的同內容重送回傳原有結果，不另記帳；同 ID 換內容會拒絕。相同 ID 曾出現在另一個連線時，新通知會保留為疑似重複的待確認項目，不自動入帳；切換自動連線也不會讓它再自動記一筆。不同連線的 ID 未必使用同一套編號，這種情況不會悄悄合併或丟棄通知。

沒有穩定 ID 時，同額、同文字不一定是同一筆消費，會保留待確認，不能靠金額自動合併。網路逾時後先重新整理收件匣，確認是否已入帳。

自動入帳授權綁定解析格式版本。新增或放寬解析格式要重新確認；測試通知、多金額通知及人工改寫金額不能作為自動格式的證據。

## 隱私及復原

- 通知原文屬私人帳務資訊，存於自己的雲端收件匣；金鑰只保存雜湊。收件匣是雲端功能，不包含在既有本機 JSON 帳本備份中；已匯入的支出則沿用既有備份與同步。
- 通知缺漏、系統停用自動化或捷徑失敗不會自動補抓歷史消費。請定期比對支付明細。
- 停用連線後，舊金鑰不可再接收；已入帳支出不會被刪除。修正已入帳項目請使用既有支出編輯／刪除流程，不要重送通知修正。
- 網路請求逾時可能已在雲端完成。重新整理收件匣與帳本，以伺服器狀態為準；確認入帳重試不會新增第二筆，也不會復活已刪除交易。
- 帳號切換會清除畫面中的通知、金鑰與草稿；不會把上一個帳號的非同步結果顯示給下一個帳號。

## 開發、驗證及發布

本功能包含 additive migration、`finance-shortcut-receive` Edge Function 和 App 介面。新接收端使用自訂金鑰，所以 Supabase 平台 JWT 驗證關閉，函式內仍必須手動驗證金鑰，資料庫 intake RPC 僅授權 `service_role`。這不授予匿名者任何帳本讀取或寫入權限。

本機檢查：`npm run lint`、相關 Vitest 測試、`npm run verify:migration`、`npm run verify:shortcuts`、`npm run build`，以及捷徑介面的瀏覽器驗證。PGlite 測試只用合成資料，不連線正式資料庫；通過不等於真機或正式環境已驗收。

正式發布依 [PRODUCTION_RELEASE.md](./PRODUCTION_RELEASE.md) 另行授權：確認拓樸與獨立資料庫備份，先新增 migration，再部署 receiver，最後發布 App。不能將僅有接收網址視為後端已部署。請先用 `test: true` 驗證，再人工核准合成或獨立測試帳戶資料；不要為 smoke test 增加使用者的真實財務紀錄。

撤回時先停用通知自動化／連線或暫停 receiver，再回復 App 版本。保留兩張新增資料表及已入帳交易，不執行 drop 或批次刪除；來源回復不能取代資料庫備份。來源還原基準為 `checkpoint/20260927-162459-before-code-smell-refactor`，SHA `8f97b3e512cc13ec222458f19edc22274472c39c`；以正常 revert／新分支回復，不重寫已推送歷史。
